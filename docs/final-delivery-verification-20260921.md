# 复杂任务最终交付验收

日期：2026-09-21。版本：`2.3.0-rc.8 + Unreleased`。修改前快照为 `frontend-backup/20260921-pre-final-delivery-verification.zip`。

## 实现边界

本批把“完成了一串调用”与“最终答案满足要求”分开。适用于有执行步骤且分类为 `hard`、`complex` 或 `full-workflow` 的持久任务，包括符合条件的聊天任务、模板、Nexus 和插件委托任务。普通对话和普通小组不强制进入额外检查；独立外部 Harness 执行不冒充已经被此 Orchestrator 门禁覆盖。

流程为：中间成果审核 -> 抽取当前用户要求 -> 一次原文合同复核 -> 最终汇总草稿 -> 逐项复核 -> 至多一次纯文本修正 -> 通过交付，或保留草稿等待补充/部分接受。合同复核只看到原始来源与候选要求，不看到最终答案；复核失败不继续认证候选合同。已有中间 Reviewer 的未解决项不会被最终语义通过覆盖。Reviewer 高分但存在 gaps/corrections，或返回截断内容，也不能自动批准。

- 要求只能引用任务输入和当前任务经已有权限检查接收的操作者补充原文，不额外声称公共账户身份已经可信。任务输入可能含历史，因此提示明确排除助手自己的承诺、第三方引文和假设示例；后续指导覆盖冲突的旧要求。
- 原文最多 48,000 字符、要求最多 24 条、最终正文最多 64,000 字符；完整序列化检查请求最多 76,000 字符，超界不是截断后假验收，而是待核对。附加执行上下文是有界摘录，不等于全部证据已核实。
- 验收同时看到原始要求与清单，清单漏项、弱化或歧义须记为 unknown。逐项返回 `satisfied / unsatisfied / unknown`，不得少项、多项或伪造引用。通过项必须引用最终正文中的准确原文；顶层状态由服务端根据明细推导。这仍是模型检查，不能证明模型从未漏判。
- 提取、验收和修订没有工具执行能力。JSON 数值交付可在提取要求时声明来源绑定的二元加减乘除表达式与字段路径，由服务端计算并校验最终字段，失败覆盖模型的“已满足”；不使用 eval 或执行任意代码。公式选取与来源真实性仍需语义判断，未覆盖任意数学证明或自然语言里的全部计算。
- 修订额度先写事件再调用模型，恢复时不多次尝试；未完成工具、未知副作用或缺失证据不通过文本改写伪装成完成。
- 输入/合同/正文/执行上下文绑定摘要，包含租户、用户、任务身份。PostgreSQL JSONB 的键序变化不使内容摘要变化；真实要求、工作或重跑变化会使旧接受失效。
- 草稿、回执及最后状态保存使用任务 revision。审核期间外部暂停、取消或补充要求，旧结果不会覆盖新的版本。
- 人工接受保留未通过回执，只接受具体版本的部分结果；不代表独立事实核验。界面沿用共享协作区，展示真实的整理要求、逐项复核和修正进度，不创建虚构 Graph 执行。

## 能证明什么

`requirementCoverage` 是来源绑定的模型语义复核计数，不是事实准确率。模型也可能漏抽要求或误判答案；引用存在不证明引用真实，诚实草稿也不等于完成用户要求的外部验证。

因此本批交付的是可执行、可恢复、可观测的质量约束，而不是“任意开放复杂任务保证正确”。要给出某领域准确率目标，仍须定义领域、用户验收标准、独立留出样本、事实/代码/计算验证器、样本数量和统计口径。真实外部服务现场验收与私人空间仍独立排期。

## 已记录的失败与修复

1. 旧单测和 Nexus 替身模型未识别新提取/验收阶段，出现待人工而非完成。扩充显式模拟协议并保留原输出、分支、Loop、恢复和工具次数断言，没有关闭门禁来使测试通过。
2. 审核与恢复复核发现真实缺陷：旧模板缺少 profile 漏验、JSONB 对象键序使恢复误判变化、晚到审核保存可能吸收新 revision。分别修正并补复杂模板、键序恢复与真实 notes API 并发回归。
3. 首轮真实模型为 1/2。预算用例的 `services.id` 未说明应使用服务名还是来源编号，而独立判定要求服务名；模型使用来源编号导致失败。随后仅澄清输入中两种 ID 的含义，不改 oracle。首轮报告 `qa/final-delivery-live-eval-2026-09-21T04-55-53-558Z-results.json` 保留；复测为 2/2，不记成全程一次通过。
4. 真实记录发现“证据来源尚未核对”会混入完整执行的 `runtimeGaps`，使界面误标部分执行。执行完整时不再携带这类执行缺口，事实未独立验证仍明确保留，真正 partial handoff 仍阻断。
5. 新部分交付确认在隔离入口的 portal 中未被 DOM 翻译，英文界面出现中文。改为明确的双语渲染，20 项浏览器专项通过；首轮记录在 `qa/task-actions-partial-dialog-first-failure-results.json`，没有覆写成首次通过。
6. 加入原始要求对照后的真实模型观察再次为 1/2，暴露真实误放行：`processingHoursPerDay` 为 1.25，模型理由竟写 `600/120=1.25` 并通过。失败原文保存在 `qa/final-delivery-live-eval-2026-09-21T05-11-36-223Z-results.json`。本批随后加入来源数值绑定的确定性计算，不以继续调用模型直到答对作为修复；强制模型始终误判的集成回归验证错误被拦、一次修订仍错则等待。
7. 第一轮总门禁 `45 passed / 1 unstable / 3 skipped`。搜索 smoke 以回答出现其他服务商名称判断发生了旁路搜索，不能区分来源引用和实际执行。修正为路由/模型/配置隔离/失败不降级检查，补独立原生搜索 transport 网络边界测试及每次脱敏诊断；首轮缺少正文证据，因此不臆测命中哪个名称，也不倒改该轮为通过。
8. `05-21-25-637Z` 实测为 0/2：正向答案正确但提取公式把每日量再除以天数、预算只减一天费用；负向任务已因实际执行缺口拦截，但 oracle 不接受运行时 partial 覆盖语义状态。修复后者只允许明确 partial 与非空缺项，保留未知草稿、零副作用等全部约束；旧报告不修改。
9. 增加一次 source-only 合同复核后，`05-31-01-211Z` 实测为 1/2：负向正确拦截，正向仍失败。模型合同文字写总预算减总费用，表达式却只减日费；修订曾将正确余额改错，虽终态未误放行仍是实际质量缺陷。随后向最终评估提供服务端实际公式计算明细，保留语义 unknown/unsatisfied 原因，不以算术覆盖；公式 unknown 时不自动文本纠错。该最后修复尚未再次真实模型验收，不宣布通过。

## 验证记录

阶段记录：原文/合同与算术专项 28/28；合同复核接入后五文件 focused 137/137（交付集成 37 项）；独立最终交付 oracle 36/36；共享协作浏览器 21/21；固定业务 24/24。最后计算明细补丁仍需整体验证，不用较早源码的通过替代。

显式真实模型命令 `npm run qa:delivery-live` 使用当前文本供应商，最多 40 次请求、每例 10 次、每次 4096 输出 Token、480 秒总期限。已保存五轮观察，依次为 1/2、2/2、1/2、0/2、1/2；最新 14 次调用。每次重测前有明确诊断或修复，不合并成首次成功率。固定两 Agent 无工具计划，不评测 Router，前置 Reviewer 排除以单独检验最终门禁。临时 SQLite/Artifact 与环境白名单隔离；无用户历史、外部发送或自动人工批准。

较早快照的无密钥 CI 已退出 0（840 测试：822 通过、18 条件跳过）；最后源码的完整门禁尚未收口。用户随后提出 Jev 决策路由评估，转入只读调研，没有擅自替换模型。日常服务未重启，未提交或推送远端。

当前未覆盖：任意领域事实正确率、复杂公式语义证明、舍入规则和千分位、未进入原始来源集的附件数值，以及 JSON 正文后追加 Artifact 链接时的算术解析。Jev 等额外判断模型也不能替代这些验证器或消除这些边界。
